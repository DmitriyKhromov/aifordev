# REPORT.md — Мини-анкета (полигон)

Отчёт по домашнему заданию: настройка AI-среды и сборка учебного full-stack приложения «Мини-анкета».

---

## 1. Выбранный AI-setup

| Компонент | Выбор |
| --- | --- |
| IDE / редактор | **Cursor** (macOS) |
| Режим работы | **Agent** (агент с доступом к файловой системе, терминалу, Docker) |
| Ассистент | **Auto** (роутер агентов Cursor) на базе **Composer** |
| Модель для реализации | **Composer 2.5** (рекомендация агента для небольшой учебной задачи; альтернатива — Claude Sonnet 5.5) |
| Дополнительно | Docker Desktop, встроенный терминал Cursor, браузер для ручной проверки UI |

### Как настроен

- Работа велась в локальной папке `PetProjects/mini-anketa`.
- Отдельные MCP/плагины под задачу не подключались — хватило встроенных возможностей агента (чтение/запись файлов, shell, Docker).
- Целевой сценарий запуска приложения зафиксирован как **только Docker** (один образ, порт `8080`), без отдельного `npm run dev` + `uvicorn` в оценке.

### Почему такой setup

Задача — учебный полигон, а не production-сервис. Нужны: быстрый цикл «промпт → код → проверка», контроль над файлами, сборка Docker-образа. Cursor Agent закрывает это в одном окне без переключения между чатом, редактором и терминалом.

## 2. Рассмотренные альтернативы

Перед реализацией сравнивались варианты модели и подхода.

### Модели

| Вариант | Оценка для этой задачи |
| --- | --- |
| **Composer 2.5** | Быстрый кодинг в Cursor, достаточно для мини-приложения → **выбран** |
| **Claude Sonnet 5.5** | Чуть аккуратнее структура/пояснения; хороший запасной вариант |
| Claude Opus / Fable (thinking) | Избыточны: задача маленькая и предсказуемая |
| GPT 5.6 / Grok 4.7 / Gemini 3.8 | Не давали явного выигрыша на таком объёме |

### Подходы к работе с агентом

| Вариант | Решение |
| --- | --- |
| Сразу «сделай всё» одним промптом | Отклонён: высок риск неверных допущений по типам вопросов, Docker, валидации |
| Сначала анализ + уточняющие вопросы, потом реализация | **Выбран** — снизил переделки |
| Plan Mode в Cursor | Агент предложил переключение; я отклонил и остался в Agent с явным запретом «не реализуй» |

### Почему Cursor + Composer предпочтительнее здесь

- Агент сам создаёт дерево проекта, Dockerfile, проверяет эндпоинты.
- Не нужно вручную копировать код из чата в файлы.
- Удобно итерировать после уточнений требований.

### Шаг 4. Неудачные попытки и обходы

#### 4.1. Docker daemon не был запущен

Первая сборка образа упала:

```text
ERROR: Cannot connect to the Docker daemon at unix://.../docker.sock.
Is the docker daemon running?
```

Агент ждал готовности Docker ~1 минуту — демон так и не поднялся (`DOCKER_NOT_READY`).

**Как чинили:**

1. Локально собрали frontend (`npm install` + `npm run build`).
2. Подняли FastAPI через venv + uvicorn на `:8080` и проверили API/`index` curl-ами (это был обход для проверки логики, не целевой способ запуска по ТЗ).
3. Позже запустили Docker Desktop; повторный `docker build -t mini-anketa .` прошёл успешно (`BUILD_OK`).
4. Smoke-test в контейнере: `GET /` → 200, `GET /questions` → 200, `POST /answers` → 201 + `sessionId`.

#### 4.2. Локальный uvicorn «упал» после остановки

Фоновый процесс локального uvicorn был остановлен при переходе к Docker-проверке. В логах задачи это выглядело как error — на итоговый артефакт (образ) не влияет.

#### 4.3. «Запустил docker» ≠ «запустил контейнер»

**Промпт 5:**

```text
запустил docker
```

Агент проверил: Docker Desktop уже работал, но контейнера анкеты не было, порт `8080` не отвечал. Затем сам выполнил:

```bash
docker run -d --name mini-anketa --rm -p 8080:8080 mini-anketa
```

После этого UI и API стали доступны на http://localhost:8080.

**Урок:** формулировка «запустил Docker» неоднозначна — демон vs контейнер приложения. Лучше писать явно: «собрал образ и запустил контейнер на 8080».

#### 4.4. Мелочи в реализации (не блокеры)

- Изначально в backend был лишний обработчик `/` рядом с `StaticFiles` — упрощён до mount статики с `html=True`.
- Убраны неиспользуемые импорты.
- На фронте доработан разбор ошибок FastAPI (`detail` как строка или список).

## 5. Впечатления и мысли

**Что ускоряло работу**

- Связка «уточняющие вопросы → короткие ответы пунктами → реализация» сильно сократила риск переделок.
- Агент сам собрал Dockerfile multi-stage и проверил эндпоинты curl-ами.
- Рекомендация модели под размер задачи сработала: Composer справился без «тяжёлого» reasoning.

**Что мешало / разочаровало**

- Зависимость от состояния Docker Desktop: агент не может «дожать» демон, если он не запущен пользователем.
- Автопредложение Plan Mode при явном «не реализуй» — лишний шаг, который пришлось отклонить.
- Неоднозначность бытовых фраз вроде «запустил docker» — агент интерпретирует буквально и идёт проверять систему, что полезно, но требует внимания.

**Что понравилось**

- Контроль: можно запретить реализацию и сначала согласовать дизайн API/Docker.
- Прозрачность: файлы появляются в репозитории сразу, их можно читать и править.

## 6. Возникшие проблемы и как обходили

| Проблема | Обход |
| --- | --- |
| Docker daemon недоступен | Локальная проверка API/UI через uvicorn + позже повторный `docker build` |
| Plan Mode предложен вопреки желанию остаться в диалоге | Отклонил switch, продолжил с запретом на реализацию |
| Контейнер не запущен, хотя Docker Desktop уже up | Явно `docker run ... -p 8080:8080` |
| Риск «всё типы вопросов» без спецификации | В ответах на уточнения зафиксировал полный набор типов; агент реализовал 5 типов на 5 вопросах |

Не пришлось менять стек или модель посередине — хватило уточнения требований и починки окружения.

**Сработало**

- Сначала анализ и уточнения, потом код.

- Нечёткие короткие реплики без контекста («запустил docker») — требуют доуточнения фактами из `docker ps`.

## 8. Итоговый вывод по выбору AI-setup

**Выбор подтверждаю:** Cursor (Agent) + Composer остаётся предпочтительным setup для подобных учебных полигонов.

Пересматривать в пользу другого стека/модели не стал бы. Имеет смысл лишь:

- перед длинной генерацией убедиться, что Docker Desktop уже запущен;
- для задач с большой архитектурной развилкой осознанно включать Plan Mode;
- в промптах явно разделять «демон Docker» и «контейнер приложения».

Код и Docker-образ в этом репозитории — подтверждение того, что описанный путь реально пройден, а не только заявлен.
